# 故障排查与验收

| 现象                    | 排查                                                                                                               |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 配置/凭据错误           | 核对 JSON 字段、文件所有者与 0600/0400 权限；错误不回显敏感输入                                                    |
| Slack 有消息但 dot 不醒 | 检查用户是否给当前个人 dot 建了受限官方事件自动化、应用已入频道、允许桥 bot 作者和线程事件；@ 或 DM 不代表订阅成功 |
| 只有图片准备消息        | 查图片段状态；必须完成外部上传才发就绪标记                                                                         |
| dot 回了但微信没收到    | 检查 team/channel/user/bot/app，回复的 thread_ts，最终标记及原微信 context 是否仍有效                              |
| 新消息持续失败          | 查看固定中文错误分类；检查令牌撤销、频道成员权限、限流和 session 过期                                              |
| 地址被拒绝              | 核验官方分区主机再显式配置；禁止添加任意 URL、私网或通配域名                                                       |
| `uncertain`             | 人工对照远端实际消息；程序不会自动重送，勿清空队列碰运气。当前没有“强制重试”命令                                   |
| 上下文过期              | 由本人发新微信消息，旧回复不移植到新上下文                                                                         |
| 状态容量已满            | 停服务并备份敏感状态，核对磁盘配额，调整容量；保留墓碑，否则历史重放可能重复转发                                   |
| 进程运行锁              | 同一 state 只能运行一个实例；异常断电锁在 120 秒失效，不要同时启动多个副本                                         |

## 用户醒来后的一次性配置

1. 在安全文件配置桥 Slack bot/app 令牌，确认必要权限与专用频道成员。
2. 在非敏感配置填写真实团队、频道、桥身份与 dot 三重身份；不要把这些贴到公开仓库。
3. 用户在自己的个人 dot 建立受限官方 Slack 事件自动化，采用文档里的就绪/最终标记约定。桥不修改现有临时任务。
4. 在最终部署主机交互扫码，由扫码身份绑定本人私聊。若返回未知官方分区域名，核验后补白名单。
5. 进行下列真实验收，合格后再决定生产部署。

## 真实验收清单（尚未执行）

微信文字 → Slack 真消息；微信图片 → Slack 可打开的真文件；dot 文字 → 同一微信会话；dot 图片 → 微信 IMAGE，并比较原始字节或下载文件哈希。再验证至少三轮连续对话、并发/乱序、断网后重启、部分图片失败、错误身份和陌生人拒绝，观察官方自动化批处理与重复出站保护是否阻止后续回复。

离线测试覆盖真实 HTTP 假服务的四条适配器路径，不使用真实账号。Socket Mode SDK 与平台自动化的端到端连通性、微信真实二维码、真实 CDN 地域地址和图片显示效果需要现场验收。不得把离线成功描述为“微信已接通”。

首次启动无转发：检查是否已读取状态目录 `启用确认.txt` 并由扫码本人发送整行文字。缺少合法 `create_time_ms` 的确认或业务消息会隔离，不能用本地接收时间补齐；确认同毫秒的业务消息请重新发送。持续“微信同步暂停”可能是未来消息时间或本机时钟回退，检查主机时间同步后重试；不要删状态或回退启用边界。未确认时消息只在本机限时缓冲，不上传图片或发 Slack。

## Slack 图片申请上传地址失败与单条恢复

上传申请及完成发布均使用 `application/x-www-form-urlencoded; charset=utf-8`。`length` 为十进制字节数，完成接口的 `files` 为 JSON 数组字符串再经表单编码；实际图片字节仍原样 POST 至上传地址。官方 [申请接口](https://docs.slack.dev/reference/methods/files.getUploadURLExternal/) 和 [完成接口](https://docs.slack.dev/reference/methods/files.completeUploadExternal/) 页面均列出 JSON 与表单，但实际验收中申请接口的 JSON 请求返回 `invalid_arguments`、同参数表单成功，因此本桥固定使用表单。不能把假服务通过当作真实接口兼容性的证明。

新日志和 `jobs.error` 只输出固定上传阶段（申请上传地址、上传图片字节、完成图片发布）及白名单错误码。未知服务端错误统一显示“未识别错误”，不记录响应体、错误描述、正文、令牌、签名 URL、文件 ID 或身份。发布阶段的未知发送结果仍为 `uncertain`，不能按准备失败处理。

旧版只存“Slack 拒绝请求”，**无法单凭该字段证明失败阶段**。仅当操作人员已独立核实该图片任务在申请地址时被明确拒绝、从未完成发布时，才能执行以下恢复。临时测试取得但未使用的上传 URL 不需要写入状态；恢复会重新申请。若无法确定，保持原状态，禁止批量重置。

1. 停止桥进程，保留配置、凭据、整个状态目录和数据库。更新审核后的提交并构建新镜像，暂不后台启动。
2. 在同 UID、同状态挂载的新镜像中，以只读数据库查询指定根线程的 `slackImage` 任务。只读取 `id/kind/status/error/created` 和根线程，不输出 `payload/context`。核实根任务为 `done`、就绪任务为 `pending`，该来源没有 `sending/uncertain`，目标未超过 TTL。记录**唯一目标任务 ID**，不能将其他失败任务顺带恢复。
3. 使用下方维护函数，只恢复记录的 ID。函数复核所有条件，持有与桥相同的目录锁，并在事务中要求恰好更新一条；仅修改其 `status/due/error`，不重建根消息、不改游标、边界、来源映射或去重记录，不更新任何 `done/uncertain`。
4. 正常启动桥，观察该图片及随后就绪消息进入原线程。不要重新发送原微信消息来代替恢复，不要再次运行已成功的恢复。

例如 Compose 服务名为 `bridge` 时，先停止该服务，然后在部署主机交互终端执行。将两个占位参数替换为刚核实的任务 ID 和原根线程；布尔值 `true` 是操作者对“只在准备阶段失败”的明确确认，不是程序推断结果：

```bash
docker compose run --rm --no-deps -T bridge node --input-type=module - '已核实的任务ID' '原根线程时间戳' <<'JS'
import { config } from './dist/src/config.js';
import { retryFailedSlackImage } from './dist/src/recovery.js';
try {
  const c = config(process.env.BRIDGE_CONFIG ?? '/app/config.local.json');
  await retryFailedSlackImage(c, process.argv[2], process.argv[3], true);
  console.log('已将唯一核实的图片准备任务恢复为待处理，其他任务未修改。');
} catch {
  console.error('恢复未完成，请检查进程锁、目标任务及恢复前提；不要绕过检查或批量重置。');
  process.exitCode = 1;
}
JS
```

Compose 名称和挂载应使用现有部署配置；维护过程不需要读取 Slack 令牌或微信 session。函数只支持这次确定的参数拒绝故障及兼容旧版通用错误；其他故障应另行对账，不能修改错误码来绕过限制。
